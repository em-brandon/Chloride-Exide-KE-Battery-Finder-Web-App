Plan: Staging Area, Conflict Resolution, Vehicle Change Notifications & Versioning
Context
When users stop the web-validate pipeline mid-run (definitive stop, not pause/resume), partially matched vehicles sit in the results table with no review step. The user needs:

A staging area that captures records from a stopped run for data validation
Conflict detection + resolution when staging and master table diverge
Notifications when the vehicles table (vehicle_years) is updated so the user knows to re-run the pipeline
A versioning/changelog system on the master table each time staging is committed
Navigation warning before staged data is discarded
Architecture Overview
Table	Role
web_battery_validation	Master table — approved, committed, versioned results
web_battery_staging	New — temporary holding area for a stopped run, pending validation and conflict resolution
web_battery_validation_versions	New — immutable log of every merge commit (one row per commit)
web_battery_validation_changelog	New — row-level diff of what changed per version
pipeline_run_log	New — tracks when each run completed, for vehicle-staleness checks
Pipeline continues to write to web_battery_validation as it runs (no change to runtime behavior).
On STOP: records from this run are copied to web_battery_staging with validation + conflict flags applied.
On Resume: pipeline continues writing to master, staging untouched.
Pre-commit check: detects conflicts (same key exists in master with different values written by a newer run or manually).
Commit: user resolves conflicts → valid records upserted to master → version + changelog entries written → staging cleared.
Discard: run's records removed from master → staging cleared.

Step 3 — Backend (admin_router.py)
Modify: POST /api/admin/pipeline/web-validate/cancel
After setting cancel event, wait up to 3 s for thread to exit, then:

Query web_battery_validation WHERE run_id = state["run_id"]
Copy rows to web_battery_staging, applying validation per row:
is_valid=FALSE, invalid_reason="Ah out of range (20–250)" — if ah < 20 or ah > 250
is_valid=FALSE, invalid_reason="Unknown technology" — if technology not in {MF, AGM, EFB, GEL, WET}
is_valid=FALSE, invalid_reason="No battery code resolved" — if battery_code IS NULL
For each staging row, check if master already has a row with same (make_n, model_n, year) and different run_id → mark conflict=TRUE, store conflict_detail JSON
Insert pipeline_run_log row with status='cancelled'
Return { staged_count, invalid_count, conflict_count } in response
New: GET /api/admin/pipeline/web-validate/staging
Paginated staging records.
Params: page, page_size, filter (all | valid | invalid | conflicts).
Top-level: has_staging, total, valid_count, invalid_count, conflict_count, run_id.

New: GET /api/admin/pipeline/web-validate/staging/pre-commit
Re-runs conflict detection against the current master table state (in case master was updated since staging was captured). Returns updated conflict list. Call this immediately before showing the commit modal.

New: POST /api/admin/pipeline/web-validate/staging/commit
Body: { conflict_resolutions: [{ make_n, model_n, year, keep: "staging" | "current" }] }

For each valid staging row with no conflict (or keep="staging" resolution): upsert to master, set version_id to new version
For each keep="current" conflict: skip (master row unchanged)
Delete invalid staging rows from web_battery_validation
Insert web_battery_validation_versions row → get version_id
Insert web_battery_validation_changelog rows (diff old vs new values)
Truncate web_battery_staging
Return { version_number, committed, removed_invalid, conflicts_resolved }
New: POST /api/admin/pipeline/web-validate/staging/discard
Delete all web_battery_validation rows WHERE run_id = staging.run_id
Truncate web_battery_staging
Return { discarded }
New: GET /api/admin/pipeline/web-validate/versions
Returns list of version entries (paginated), newest first.
Includes: version_number, committed_at, committed_count, removed_count, conflict_count.

New: GET /api/admin/pipeline/web-validate/versions/{version_id}/changelog
Returns row-level changelog for a specific version.
Shows each changed (make_n, model_n, year), change_type, old vs new values.

New: GET /api/admin/pipeline/web-validate/staleness
Returns:

{
  "last_run_completed_at": "ISO timestamp or null",
  "vehicles_last_updated_at": "ISO timestamp",
  "new_vehicles_since_last_run": 42,
  "stale": true
}
Logic: query MAX(created_at) from vehicle_years, compare against latest finished_at in pipeline_run_log WHERE status='completed'. Count combos in vehicle_years not in web_battery_validation.

Conflict Resolution Logic (server-side)
A conflict is when staging has (make_n, model_n, year) AND master already has a row for the same key with any of these true:

run_id differs (master was written by a different, newer run)
ah value differs by more than 5 Ah (noise tolerance)
technology differs
Non-conflicting updates (same values, different source, same run) are upserted silently.

conflict_detail JSON shape:

{
  "current": { "ah": 60, "technology": "MF", "source": "carapi", "run_id": "abc" },
  "staged":  { "ah": 75, "technology": "AGM", "source": "tavily" }
}
Validation Thresholds (server-side, applied when staging is populated)
Check	Condition	Reason
Ah too low	ah < 20	"Ah value out of range (20–250)"
Ah too high	ah > 250	"Ah value out of range (20–250)"
Bad technology	not in {MF, AGM, EFB, GEL, WET}	"Unknown technology type"
No battery code	battery_code IS NULL	"No battery code resolved"
